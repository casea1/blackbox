## 1. Accuracy: things that mislead a reviewer (do first)

- **U7** A *refused* `auditctl -e 0` (rules locked with `-e 2`, CONFIG_CHANGE `res=0`) is reported High "Kernel auditing was turned OFF by claude — nothing is recorded until it is turned back on". A refused `auditctl -D` became Info "claude locked the audit rules". Honour `res=` on CONFIG_CHANGE: a refused change is "tried to turn off auditing; refused because the rules are locked" (Medium/High as an attempt), never "auditing is off".
- **U4** pam_motd runs `/etc/update-motd.d/*` (via `run-parts`) as root inside the user's session, so audit records carry the user's auid. One SSH logon by non-admin `bbuser` produced ~45 rows "bbuser ran as root: uname -o / landscape-sysinfo / cat /var/cache/motd-news…". Recognise the motd tree (parent chain sshd-session/login → run-parts `/etc/update-motd.d`) and collapse it to one Info row or drop it. Same for `sudo -i` login-shell setup (`/etc/profile.d`, `locale-check`, `debuginfod` finds): keep the user's real commands, not shell start-up noise.
- **U5** OpenSSH 10 splits sshd into `sshd` + `sshd-session`; each failed password gives two PAM records ("via SSH" and "via sshd-session"), so 6 attempts = 12 rows and the detection says 14. Merge them (C4 did this for successful logons).
- **U6** A spray of unknown names (admin, oracle, test, guest, ubuntu, postgres; 1 try each) gave 3× "(unknown user name) … does not exist" + 1× "<name> via SSH — **wrong password**" per name, and the detection was "password guessing for (unknown user name)" instead of "One source tried several accounts". Get the tried name from `auth.log`/journal ("Invalid user admin from ::1") or the PAM record and correlate; fix the wrong reason text; make the spray detection fire.
- **U11** `mount -t tmpfs none /mnt` → Medium "claude mounted a disk" (removable media). Check fstype/source (tmpfs, proc, nfs, cifs, bind, overlay are not disks) before calling it removable.
- **U8** "The audit service (auditd) was stopped by root" — the DAEMON_END record says auid=root because systemd (PID 1) sends the signal, but `claude` ran `systemctl stop auditd` one second earlier. Attribute the stop to the person from that preceding command (AU-3).
- **L3** A sender's `blackbox status` showed healthy 40 s after `systemctl stop auditd` ("Settings checked" was earlier; checks run daily/after restart). On every collection check auditd is active and `auditctl -s` enabled; show red in `status` and in the collector's view of that system. Ubuntu 26.04's auditd unit does not refuse a manual stop.

## 6. New feature, behind owner approval: SCAP results in the report

Don't implement or bundle a SCAP scanner (assessors expect results from a validated tool with current DISA benchmarks: SCC, or OpenSCAP with the DISA/SSG content; SCC can't be redistributed; benchmarks change quarterly; it breaks the small/read-only/no-dependency posture). Instead, **ingest results the site already produces**, the way PowerStrux puts a scan next to its audit report. First write a short design note in `docs/design.md` for the owner to approve, then implement:

- `scap_results` setting: a folder Blackbox reads (read-only) for the newest XCCDF results (`*XCCDF-Results*.xml` from SCC, `oscap xccdf eval --results` / ARF on Linux). Parse with `encoding/xml` (stdlib).
- Per system: benchmark title/version/date, profile, scan time, score, pass/fail/not-checked counts, **open CAT I / II / III** (severity high/medium/low), and change since the previous scan (newly failed, newly passed).
- On the report: a "STIG compliance (SCAP)" section on Audit health and the Systems page, with **stale-scan warning** (older than a configurable `scap_max_age_days`, default 30/90) and "no scan found". Open CAT I in the Overview's important items.
- Evidence: copy the results file into the report folder (hashed in manifest.sha256), like the original logs.
- LAN: senders ship their newest results file with their batches (same integrity checks as log archives).
- CSV export of open rules (rule ID / Vuln ID / CAT / title / system) for the POA&M.
- Optional and opt-in only, later: if `scc_path` points at an installed SCC (`cscc.exe` / `cscc`), run it on its own schedule (not the hourly collection), with a timeout and low priority. Never change settings; never run a remediation.
- Not in scope: GPO changes or remediation. Audit health may keep listing the Group Policy path to fix a setting, as now.
