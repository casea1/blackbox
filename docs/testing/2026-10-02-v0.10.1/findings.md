# Blackbox 0.10.1: findings (Windows collector + Ubuntu sender)

Tested 2–3 Oct 2026 on two Umbrel VMs: `windows-11` (Windows 11 25H2, meant as the collector) and `ubuntu-server` (Ubuntu 26.04 LTS, sender over SMB). The Windows VM ran under software emulation and never finished installing (still at "Just a moment…" after 14 hours), so nothing here was seen on a live collector: Windows items come from offline `blackbox report --xml` runs and the source. Every action is in [test-activity.log](test-activity.log); the plan is [test-plan.md](test-plan.md).

"Confirmed" means seen live. "Offline" means reproduced with `blackbox report` on synthetic logs on another Linux host. "Code only" means taken from the source, not reproduced.

## New findings

| # | Finding | Status |
|---|---|---|
| L3 | **A sender's `blackbox status` doesn't notice auditd has been stopped.** `sudo systemctl stop auditd` succeeded on Ubuntu 26.04 (the unit doesn't refuse a manual stop) and `status` 40 s later showed a healthy sender: "Last collection 21:31 (just now), Settings checked 21:21". Audit settings are re-checked daily and after a restart (C5), so a sender can run without auditd for up to a day with no sign in `status`, and the collector's tray/status only learns at the next daily check. Collection itself knows: it read no new audit records. Suggest checking `auditd` is active (and `auditctl -s` enabled) on every collection, and treating "stopped" as red. Whether the stop itself is reported as High is checked on the collector. | Confirmed |
| L4 | **Sender install and errors talk about reports and a local path.** The installer prints "Scheduled: blackbox.timer — collects every 15 minutes as root; **weekly reports**" on a sender, which makes no reports. | L5 | **`config set exclude_users none` excludes an account named "none".** `none` clears LAN settings, an empty string clears lists. Using one word for both, or rejecting `none` for a list, would avoid hiding a real account by accident. | Confirmed (minor) |

## Windows Server 2025 collector, live

Collector: Windows Server 2025 Evaluation (build 26100.1, unpatched GA) on the Umbrel, installed with the setup window as "This is the collector", inbox shared. Windows 11 never finished OOBE on this rig (nested virtualization; see test-activity.log), so Server 2025 (also supported) was used. The Umbrel isolates its VMs from each other, so the sender delivered over the documented **SFTP (sshfs) route** through a tunnel on the tester host; SMB delivery between the VMs couldn't be tested here.

| # | Finding | Status |
|---|---|---|
| N2 | **Sharing the inbox doesn't open the firewall, and nothing says so.** Server 2025 ships "File and Printer Sharing (SMB-In)" disabled on every profile (and the network was Public). Setup shared `C:\BlackboxInbox` and finished "Other computers can now send to this collector's inbox" without enabling the rule or warning; `blackbox status` on the collector shows Inbox OK. A sender then gets port 445 refused. Either enable/scope the SMB-In rule when sharing (to the senders' addresses if known), or at least check it and say so in setup and in `status`; and document it in lan.md. | Confirmed |
| L6 | **The sender's error hides the cause.** With the collector refusing port 445 (and later with the VMs unable to see each other at all) every attempt said only "collector inbox not available: /var/lib/blackbox/collector (is the shared folder connected or mounted? on the collector, the folder must be set as its inbox)". The mount unit's own error ("Error connecting to socket", `-113` no route to host) is in dmesg but not in Blackbox's message or `status`. Surface the mount/connection error (and name the share, L4). | Confirmed |
| S11 | **Setup window: no field for which accounts may deliver over the network.** With "Share it on the network" ticked, the only accounts box is the VirtualBox one; the admin must run `net localgroup "Blackbox Senders" <account> /add` afterwards (as lan.md says). Show an "Accounts allowed to deliver" field whenever the inbox is shared or used by VMs. | Confirmed |
| S12 | **"Virtual machines on this PC send to it (VirtualBox shared folder)" is ticked by default with the current user pre-filled**, on a server with no VirtualBox. Accepting defaults adds the logged-on admin to Blackbox Senders for nothing. Default it on only if VirtualBox is installed. | Confirmed |
| S13 | **The share allows offline caching** ("Caching: Manual caching of documents", the `net share` default). Use `/CACHE:None` so Windows senders don't keep cached copies of audit batches. | Confirmed (minor) |
| W1 | **A computer's previous name becomes a second system.** The first report on a freshly installed server was named `2026-10-04_0005_2-systems` and listed `WIN-R5L5B9EF403` (the name Windows had before OOBE renamed it) with 6 events. Any newly imaged or renamed PC will show a phantom system. The LAN import already avoids this ("Systems are only the computers that collect"); do the same for the local log, or fold old names into the current one. | Confirmed |
| W2 | **Every Windows OpenSSH session is a "First use of administrator rights" (Medium).** OpenSSH for Windows runs each session as a virtual account `VIRTUAL USERS\sshd_<pid>`; 17 SSH sessions gave 17 Medium detections, each a "new" admin. Attribute to the real user (the 4624 for the session names `claude`) or treat `VIRTUAL USERS\sshd_*` as one service identity. | Confirmed |
| W3 | **89 Medium "PowerShell script typed or run from memory … flagged as suspicious" from routine firewall cmdlets.** PowerShell writes Warning-level 4104 for script blocks containing keywords it considers suspicious, including the generated CDXML wrappers of its own modules (`$__cmdletization_*`, NetSecurity). A few `Get-/Set-NetFirewallRule` calls produced 89 Medium rows, one per fragment of multi-part script blocks. Join parts of one ScriptBlockId (MessageNumber/MessageTotal) into one row, and recognise Microsoft's CDXML-generated module code. As it stands the PowerShell page drowns real findings (D4 decoding is good). | Confirmed |
| W4 | **Windows setup noise: 28 Medium "SYSTEM renamed account X to X"** (old and new names identical) from OOBE, plus D7 from 0.10.0 still present ("added claude to the group None", 4728 for the default primary group). Skip 4781 when the names are equal and 4728 for "None". | Confirmed |
| L8 | **On the SFTP (sshfs) route, the sender stops collecting whenever the collector is unreachable.** Blackbox puts the `send_to` folder in the service sandbox (`ReadWritePaths=... -/mnt/blackbox-inbox`). When the sshfs connection is down, systemd can't set up the namespace and `blackbox.service` fails before Blackbox runs: `status=226/NAMESPACE "Failed to set up mount namespacing: /mnt/blackbox-inbox: Input/output error"` (and "Transport endpoint is not connected" with an automount). So no collection happens at all for the length of the outage, not just no delivery; the shutdown unit fails the same way. Events wait in the local logs and are caught up when the link returns (sshfs `reconnect` recovered and the next run sent the backlog), but a long outage on a busy system can let logs rotate away, which breaks "a computer that is off or cut off loses nothing". The `-` prefix only tolerates a missing path, not EIO. **Fix principle: a delivery problem must never stop collection.** E.g. run delivery in a separate unit (`blackbox-send.service`) whose failure doesn't affect collection, or have Blackbox manage an sshfs mount unit itself (as it does for SMB, under `/var/lib/blackbox/collector`) and check reachability inside the program. Also check whether a dead *established* CIFS mount (hard mount, server gone) does the same on the SMB route. | Confirmed |
| L7 | **The documented sshfs fstab mapping doesn't recover from a failed mount at boot.** After a reboot while the link was briefly down, `mnt-blackbox\x2dinbox.mount` failed ("read: Connection reset by peer") and stayed failed after the link came back; Blackbox correctly refused the empty folder and queued, but nothing remounts a folder-type `send_to`, so the sender would queue indefinitely until someone mounts it by hand. `x-systemd.automount` (the usual cure) makes L8 worse (226/NAMESPACE "Transport endpoint is not connected"). For SMB, Blackbox restarts its own mount unit before each run; give the SFTP route the same (generate the sshfs mount unit, e.g. `send_to = sftp://bbsend@COLLECTOR/C:/BlackboxInbox`), or document a retrying mount (a timer that runs `mount -a`) instead of a plain fstab line. | Confirmed |
| N3 | **No post-quantum key exchange on the Windows OpenSSH side**: Ubuntu's OpenSSH 10 warns "This session may be vulnerable to 'store now, decrypt later' attacks" when using the SFTP route to Windows Server 2025's OpenSSH. Not Blackbox's code, but relevant if the SFTP route is recommended for classified networks (SC-8, SC-13). | Confirmed (info) |

Working correctly on the SFTP route: the lan.md fstab line mounts; scheduled, sandboxed timer runs deliver every 15 min (00:30-03:45, no failures); with the mapping down Blackbox refuses the empty mount point (marker check) and writes nothing into it; sshfs `reconnect` recovers after a link drop.

Working correctly on the collector: setup window flow and summary; data folder Administrators/SYSTEM only; Blackbox Senders group, share (Senders: Change only) and NTFS ACLs exactly as security.md says; STIG check (12 pass / 24 need attention, Defender intelligence 1,033 days old flagged with the GPO path); A10 confirmed (exe NotSigned; SHA256 matches); **catch-up: 114 batches + 2 original-log archives queued over ~27 h delivered in 47 s and imported with 0 rejected**; Systems shows both computers with last collection/received; Linux detections arrive unchanged; account create / group create / add to Blackbox Senders / add to Administrators (High) correct.

### Splunk-style features an ISSO would look for (not bugs; for the roadmap)

- **Account review (AC-2(j), AC-2(3)):** a per-system snapshot of local accounts, enabled/disabled, last logon, and members of privileged groups, with **dormant accounts (no logon in 35 days, the STIG limit)** flagged. Today People is built only from activity in the period, so an unused admin account never appears.
- **Catch-all and drill-down (AU-6/AU-7):** see A1: every collected event searchable, not only translated ones.
- **Near-real-time alerting for Highs:** today Highs wait for the scheduled report (tray notifications cover collection and settings, not detections). Confirm in live testing.
- **Retention guard (AU-11):** warn when `retention_days` is set below the site's requirement (commonly 365 days, or longer for classified systems).
- **Baseline/drift per system:** event volume per system per day against its own history (partly on Systems and Trends).
