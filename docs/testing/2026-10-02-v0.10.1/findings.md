# Blackbox 0.10.1: findings (Windows collector + Ubuntu sender)

Tested 2–3 Oct 2026 on two Umbrel VMs: `windows-11` (Windows 11 25H2, meant as the collector) and `ubuntu-server` (Ubuntu 26.04 LTS, sender over SMB). The Windows VM ran under software emulation and never finished installing (still at "Just a moment…" after 14 hours), so nothing here was seen on a live collector: Windows items come from offline `blackbox report --xml` runs and the source. Every action is in [test-activity.log](test-activity.log); the plan is [test-plan.md](test-plan.md).

"Confirmed" means seen live. "Offline" means reproduced with `blackbox report` on synthetic logs on another Linux host. "Code only" means taken from the source, not reproduced.

## New findings

| # | Finding | Status |
|---|---|---|
| L3 | **A sender's `blackbox status` doesn't notice auditd has been stopped.** `sudo systemctl stop auditd` succeeded on Ubuntu 26.04 (the unit doesn't refuse a manual stop) and `status` 40 s later showed a healthy sender: "Last collection 21:31 (just now), Settings checked 21:21". Audit settings are re-checked daily and after a restart (C5), so a sender can run without auditd for up to a day with no sign in `status`, and the collector's tray/status only learns at the next daily check. Collection itself knows: it read no new audit records. Suggest checking `auditd` is active (and `auditctl -s` enabled) on every collection, and treating "stopped" as red. Whether the stop itself is reported as High is checked on the collector. | Confirmed |
| L4 | **Sender install and errors talk about reports and a local path.** The installer prints "Scheduled: blackbox.timer — collects every 15 minutes as root; **weekly reports**" on a sender, which makes no reports. When the share can't be reached, the error names the mount point "collector inbox not available: /var/lib/blackbox/collector" rather than `//10.203.0.2/BlackboxInbox`, and the install prints it twice. | Confirmed (minor) |
| L5 | **`config set exclude_users none` excludes an account named "none".** `none` clears LAN settings, an empty string clears lists. Using one word for both, or rejecting `none` for a list, would avoid hiding a real account by accident. | Confirmed (minor) |
| N1 | **SMB delivery isn't encrypted (SC-8).** The Linux mount unit has no `seal` and the collector creates the share with `net share`, which can't set `EncryptData`. Batches carry user names, command lines and addresses across the LAN, protected only by SMB signing where negotiated. Suggest `seal` (SMB 3 encryption) on Linux senders and `Set-SmbShare -EncryptData $true` on the collector. Verify on the wire once the collector is up. | Code; live planned |
| V1 | **`verify` passes when a report's data file is deleted along with its manifest line.** `data/failed-20261002-raw.js` holds the rows behind the Failed logons page; deleting it and its line in `manifest.sha256` gives "OK — all files match the manifest". Same for `events.zip`. `report.html` knows which data files it loads, so verify could require them (and `events.zip`). The docs now say an unsigned manifest finds damage, not deliberate editing, so this is about accidental loss of a file and its line being undetected, which is less likely; low priority. | Offline |
| V2 | **`verify` prints a misleading second line.** With `summary.json` removed from the manifest it prints both "summary.json: not in the manifest" and "summary.json: not in the manifest (added after the report was produced)". The file wasn't added later. | Offline (minor) |
| U2 | "1 routine event by bbtest ×1": the "×1" repeats the count. | Offline (minor) |
| U3 | One admin network logon is two rows with near-identical text: 4624 "…with administrator rights" (Info) and 4672 "…with administrator privileges" (Low). Like D6 in 0.10.0. | Offline (minor) |
| U1 | **"between 18:17:02 and 18:17:02".** A detection whose events fall in the same second reads oddly; "at 18:17:02" or "within 1 second" would read better. | Offline (minor) |
| E1 | **Browser CSV export doesn't quote a bare CR.** `app.js` `Table.csv` quotes a field containing `"`, `,` or LF, but not CR alone, so a value with an embedded CR can split a row in Excel. Go's `csv.Writer` (events.csv, detections, health) handles this. | Code only (minor) |
| L1 | **One unreadable file in the inbox stops every import.** `lan.Import` returns on the first `os.ReadFile` error, so batches from every sender wait until it is removed. A sender owns the files it writes over SMB and can change their ACL. Suggest rejecting that file and carrying on. | Code only; live test planned |
| L2 | **Sender identity is the batch's own claim.** A member of Blackbox Senders can read other senders' IDs from the inbox file names and write batches as them. `security.md` already says batches are unsigned and checks don't stop a determined attacker with write access, so this is a known limit. In a domain, each computer writes as its own account, so the collector could compare the file's NTFS owner with the sender it claims to be. | Code only (design) |

## Linux sender, live (Ubuntu 26.04, auditd + Blackbox rules + STIG extras)

From `blackbox report` on the sender's own audit log and syslog after activity sets 1 and 2 (rows in shots/ubu-05..08). These are the same translations the collector will apply.

| # | Finding | Status |
|---|---|---|
| U4 | **Ubuntu's login message scripts are reported as the user running root commands.** One SSH logon by the non-admin `bbuser` produced ~45 Low rows "bbuser ran as root: uname -o", "… /etc/update-motd.d/50-landscape-sysinfo", "cat /var/cache/motd-news", "find /var/lib/update-notifier…". pam_motd runs `/etc/update-motd.d/*` as root inside the user's session, so the records carry the user's auid. To a reviewer this reads as privilege escalation by a non-admin and floods Privileged activity and People. Suggest recognising the pam_motd/run-parts `/etc/update-motd.d` tree (and `sudo -i` login-shell setup: `/etc/profile.d`, `locale-check`, `debuginfod`) and collapsing it to one "login message scripts ran" row or leaving it out. | Confirmed |
| U5 | **Each failed SSH password is two rows on OpenSSH 10** ("Failed logon for bbuser via SSH" and "… via sshd-session"), so 6 attempts became 12 rows and the guessing detection says "14 failed logons". C4 (0.10.0) was about successful logons; the same duplication now hits failures because OpenSSH 10 splits sshd into `sshd` and `sshd-session`, both logging through PAM. | Confirmed |
| U6 | **A spray of unknown user names isn't recognised, and the names are lost.** 6 unknown accounts (admin, oracle, test, guest, ubuntu, postgres), one try each, gave 24 rows: 3× "Failed logon for (unknown user name) via sshd-session — the user name does not exist" and 1× "Failed logon for admin via SSH — **wrong password**" (wrong reason) per name. The detection was "Possible password guessing: 18 failed logons for (unknown user name)" instead of "One source tried several accounts". The tried names are what an ISSO needs; auditd records them as `(invalid user)`, but `auth.log`/the journal has "Invalid user admin from ::1". | Confirmed |
| U7 | **A refused `auditctl -e 0` is reported as "Kernel auditing was turned OFF by claude — nothing is recorded until it is turned back on" (High).** The rules were locked (`-e 2`) and the change was refused (`res=0`); auditing never stopped. The refused `auditctl -D` became "claude locked the audit rules (they cannot be changed until reboot)" (Info). The result field of CONFIG_CHANGE is being ignored. A false "auditing off" is costly: it's the finding an ISSO escalates. | Confirmed |
| U8 | **"The audit service (auditd) was stopped by root".** It was stopped by `claude` (`sudo systemctl stop auditd`). The DAEMON_END record itself says auid=root because systemd (PID 1) sends the signal, so the record isn't wrong, but the command row one second earlier names `claude`. AU-3 wants the person: link the stop to the `systemctl stop/kill auditd` command just before it. The stop is correctly High (not downgraded as a planned reboot, C6), and the "Auditing was switched off for 1 minutes (21:31:31 to 21:32:56)" detection is right. | Confirmed |
| U9 | **Tampering with Blackbox itself is only Low "ran as root".** `blackbox config set exclude_users bbuser` (hides that user's routine activity from future reports), `systemctl stop blackbox.timer` and a direct `sed` edit of `/etc/blackbox/blackbox.conf` appear only as Low "claude ran as root: …" among hundreds of such rows. See A5. | Confirmed |
| U10 | **Persistence and privilege changes are only Low.** `chmod u+s /tmp/bbsh` (setuid root shell), a new root job in `/etc/cron.d/bbtest` and an `sshd_config` edit appear only as Low "ran as root". The Windows equivalents (scheduled task created 4698, service installed 7045) get their own event types and are flagged. The STIG rules that would identify them (`perm_mod`, a cron watch) are dropped (A3). | Confirmed |
| U11 | **A tmpfs on /mnt is "claude mounted a disk" (Medium, removable media).** Any mount whose command mentions `/mnt` is treated as removable media; check the filesystem type (tmpfs, nfs, cifs, bind) before calling it a disk. | Confirmed |
| U12 | "(using gnurm)": Ubuntu 26.04's GNU `rm` is installed as `gnurm` (Rust coreutils are the default), and the program name is shown as is. | Confirmed (minor) |
| O1 | **Ubuntu 26.04 uses sudo-rs, which writes no sudo audit records and doesn't log a denied sudo at all.** `sudo-rs 0.2.13` produced 0 USER_CMD and 0 USER_AUTH records since boot. `bbuser` (not in sudoers) running `sudo id` was refused ("I'm sorry bbuser. I'm afraid I can't do that") with **nothing** in the journal or audit log. Blackbox relies on USER_CMD for sudo when auditd is present, so on 26.04 sudo use appears only via the generic "ran as root" rule, without "used sudo", the target user, or failures. This is an OS change, not a Blackbox bug, but (1) Blackbox's support list should say 26.04 isn't supported until it handles this, (2) `check` could flag sudo-rs, and (3) STIG images moving to 26.04 should switch back to classic sudo (`update-alternatives`/`sudo` package) or accept that failed privilege escalation isn't logged (AC-6(9), AU-12). | Confirmed |

Working correctly on Linux: created-and-deleted account (High), user added to `sudo` (High) and removed, sudoers.d change (High), failed `su` ("claude failed to switch to bbuser with su — wrong password"), kernel module load/unload (Medium), time change (Medium), file deleted / truncated in `/var/log` (High), auditd stopped (High) with the "auditing switched off for 1 minute" detection, auditd started (Info), password guessing (High), covering-of-tracks pairing (High).

Owner decisions respected and not re-raised: no review/sign-off section (reviews are recorded on a separate platform) and no classification banner (`design.md` §13).

### Splunk-style features an ISSO would look for (not bugs; for the roadmap)

- **Account review (AC-2(j), AC-2(3)):** a per-system snapshot of local accounts, enabled/disabled, last logon, and members of privileged groups, with **dormant accounts (no logon in 35 days, the STIG limit)** flagged. Today People is built only from activity in the period, so an unused admin account never appears.
- **Catch-all and drill-down (AU-6/AU-7):** see A1: every collected event searchable, not only translated ones.
- **Near-real-time alerting for Highs:** today Highs wait for the scheduled report (tray notifications cover collection and settings, not detections). Confirm in live testing.
- **Retention guard (AU-11):** warn when `retention_days` is set below the site's requirement (commonly 365 days, or longer for classified systems).
- **Baseline/drift per system:** event volume per system per day against its own history (partly on Systems and Trends).
