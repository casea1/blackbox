## What's new

Fixes from the 0.17.0 re-test. Blackbox still only reports; it changes no system or audit settings.

### A run that dies no longer stops collection (LOCK1)

In 0.17.0, a run that was killed (a crash, `kill -9`, an out-of-memory kill, power loss) left `blackbox.lock` behind. Every scheduled run for the next two hours then failed with "another Blackbox run is in progress": nothing was collected or sent, and `blackbox status` still exited 0.

- **The lock is now an operating-system lock.** Linux uses `flock` and Windows uses `LockFileEx`. It is held for the life of the run, so the system releases it however the run ends. The file still records the process ID and start time.
- **Old lock files.** A lock file left by an earlier version counts only while its process is still running. A process that started after the lock was taken has only reused the number, so it doesn't count.
- **A run that hangs still holds the lock.** When a scheduled run gives up waiting for it:
  - `blackbox status` says "Collection is blocked: a run has held the lock since <time> (PID n)", gives the command to end that process, and exits 4;
  - the status icon turns red and says the same;
  - the next run records the gap, and the next report's Audit health shows "Collection was blocked" for that system. For a sender, this shows on the collector.

### The status icon's menu opens at once (TRAY2)

The menu used to recalculate the full status before appearing, which took about 8 seconds on a collector. It now opens straight away with the status last read, which is at most a minute old. A fresh read runs in the background and updates the icon and the next menu.

### Events lost to log rollover: which log, and what helps (LOG1)

On the Windows 11 test VM, all of the "events overwritten" since 5 Oct came from the PowerShell log:
- Windows gives that log 15 MB, and with script block logging each event can be 30 KB or more;
- so it held about 460 events, and turned over in 9 minutes between two collections 15 minutes apart.

- **`blackbox check` now sizes the PowerShell log.**
  - It recommends at least 1 GB, or enough for a week at its rate (up to 2 GB).
  - Other logs Blackbox reads (Defender, Firewall, Remote Desktop, Print, USB) are flagged only when they hold less than a week.
  - These are Blackbox's advice, not STIG settings, so a shortfall is a warning.
  - Group Policy has no Event Log Service setting for these logs. The fix gives `wevtutil sl "<log>" /ms:<bytes>`, and the registry value (`HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\WINEVT\Channels\<log>`, `MaxSize`) for Group Policy Preferences.
- **The log is named wherever a loss is shown**, for example "PowerShell log on WIN11-TEST: 447 events overwritten". This covers status, the status icon, the Overview, Audit health, the Systems page and the report warnings.
- **The advice depends on how fast the log is written.**
  - If a log turned over faster than the time between collections, it is too small for its volume, and collecting more often would not help. The advice says so and gives the size it needs.
  - "Collect every 15 minutes" is suggested only to a system that collects less often.
- **Losses are split by how serious they are.**
  - Losses from the Security log or the Linux audit log stay High ("Events lost to log rollover", red), and `blackbox status` still exits 4 for them.
  - Other logs' losses appear on their own amber line, "Other logs overwrote events", and no longer make `status` exit 4.
- **What the original logs hold.** The logs exported at each collection hold what each log had at that moment. Events written and overwritten between two collections are in no export, and the report now says so.

### Gaps from before 0.14 (L13c)

A "Missing batches" gap the collector recorded before 0.14 doesn't clear by itself, because nothing in the sender's batches says where those earlier batches went. If they went to a previous collector, record that with `blackbox gaps accept`, for example `blackbox gaps accept ubuntu-server 1-280 "went to the previous collector"`. lan.md describes this.

Release files are still unsigned: the signing secrets (A10) have not been set yet.
