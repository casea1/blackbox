## What's new

Fixes from the 0.25.0 quick re-test (8 Oct 2026). Neither item blocks production. Blackbox still only reports; it changes no system or audit settings.

### A delete known only from its command line is Medium (DET1b)

- **What happened:** `sudo rm` of a file in the collector's inbox was refused (a drop-only inbox on a CIFS share), but the report still showed a High "claude deleted Blackbox's files: /usr/bin/rm …".
- **Why:** the audit log had only the command (sudo's record and rm's `execve`). There was no record of the delete itself, because the share is CIFS and Blackbox's watch rules weren't installed. So the 0.25.0 check for a refused delete never applied.
- **Now:** a delete of Blackbox's files is High, "deleted Blackbox's files", only when a record shows it worked:
  - a file of Blackbox's deleted or changed by the same process (Linux: a `nametype=DELETE` with `success=yes`; Windows: a 4663 delete);
  - or a file the command names gone at the Blackbox run that collected it.
- With only the command line, the row is "ran rm on Blackbox's files: …" (or `del`, `Remove-Item`), **Medium**, with "Whether it worked: isn't recorded" in its details. It is listed under Medium as "delete commands on Blackbox's files (whether they worked isn't recorded)", and, like a refused delete, it is not counted as a removal.
- A file still there at that run is named in the details. A file gone from a folder Blackbox empties itself (the inbox, the outbox, the original logs waiting) doesn't count as deleted, because Blackbox may have moved it.
- `wevtutil cl` is unchanged: its row already says "ran a command that can clear logs", and a clear that happened has its own log-cleared row.

### Resent batches in blackbox.log (LOG2)

- A batch sent again that was already imported was logged as "inbox: imported …". The line now says "inbox: NAME was already imported (sent again), written by …".
