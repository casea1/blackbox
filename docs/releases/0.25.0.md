## What's new

Fixes from the 0.24.0 pre-production test (8 Oct 2026). Its verdict was go: nothing here blocks deploying 0.24.0. Blackbox still only reports; it changes no system or audit settings.

### No false gap after the collector upgrade (SEC1e)

- **What happened:** a batch waiting in a 0.23 folder at the collector's upgrade was imported. The next delivery then listed it as missing, and `blackbox send --resend` imported it a second time (seen with batch 472).
- **Why:** the upgrade starts a collection straight away, and that run imported the batch and pinned the sender's key. Setup had read the state before waiting for that run, and saved its old copy once the run finished. This undid the import: the last batch number, the hash behind "already imported", the key pin and the folder move.
- **Fixed:** whatever waits for Blackbox's lock now reads the state again once it holds it, so nothing saves an old copy. This covers every command, not only setup.
- After the upgrade, the next batch shows no gap, a resend of the waiting batch says "already imported", and the key is pinned at once.

### A refused delete is an attempt, not a removal (DET1)

- **What happened:** a delete of Blackbox's files that the operating system refused was reported as "deleted Blackbox's files … 3 times", a High detection.
- **Now:** when the audit records of the same process show the delete refused, and none shows a file deleted, the row says "tried to delete Blackbox's files (refused)", **Medium**, with each refused file in its details.
  - **Linux:** `success=no` with a non-zero `exit=` (such as `-13`, permission denied) from the program, or the one sudo started for it.
  - **Windows:** a 4656 or 4663 audit failure by the same process as the command's 4688. This needs failure auditing on `C:\ProgramData\Blackbox`.
- It is not counted as a removal: no "Blackbox's files removed" detection, and not a step of "Possible covering of tracks". Deletes that happened stay High, with their own count.
- Any failed change to a file in Blackbox's folders is now recorded, whatever the error, so it can't count as a removal either.

### The OS name comes from the inventory (OS1)

- **What happened:** on Linux, Overview, Systems and each system's page showed "Blackbox's advice" as the OS. That is the settings check's baseline, not an OS.
- **Now:** they show the OS the inventory reports, such as "Ubuntu 26.04.1 LTS" or "Windows Server 2025 Standard" (shortened in the Systems list: "Ubuntu 26.04", "Server 2025").
- With no inventory, the OS of the STIG the system was compared with is shown, then "Windows" or "Linux". "Blackbox's advice" is never shown as an OS.
- Windows systems with an inventory now show their edition too.

### Local accounts are not called domain accounts (PPL1)

- **What happened:** on a network with no domain, People said "Domain account win11-test\claude" for local accounts.
- **Now:** an account written `HOST\name` whose HOST is one of the report's computers (short or full DNS name, any case, retired ones included) is a local account: "Local account on N systems". Only an account from another domain says "Domain account CORP\name".

### Smaller (SEC1f, UI22)

- **Stray files in the inbox (SEC1f).** A file in the inbox that isn't a delivery (such as `probe.txt` or a hidden file) is moved to `inbox\rejected`, with a `.why.txt` beside it, once it hasn't changed for 10 minutes. Nothing is deleted, folders in the inbox are left alone, and `status` lists these files.
- **Key pin for batches from 0.23 folders (SEC1f).** Batches emptied from a 0.23 folder at the upgrade now pin the sender's key straight away (the SEC1e fix).
- **A replayed unsigned copy (SEC1f).** An unsigned exact copy of a batch already imported (such as the copy a sender keeps in `outbox\sent`, put back in the inbox) is removed and counted as "already imported". Any other unsigned batch claiming to be from a signed sender is still refused.
- **First delivery (UI22).** A new sender's Reporting square is green, "first delivery received 05:48", even before a collection run of its own is on record. It was grey ("no data").
- **Short fingerprints (UI22).** Overview's "Needs review" line shortens key fingerprints (`SHA256:LuoiZpT8…`). The full one is in the detection and in `blackbox senders`.
